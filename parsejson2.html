02 · The big picture

Why APIs speak JSON in the first place.

Before we touch Power Automate, let's answer the "why". Two apps need to trade information. One sends an order. The other sends back a weather forecast. They can't send screenshots — they send structured text. That text format is JSON.

{ "city": "Mumbai", "temp": 32, "sunny": true }

It's human-readable, machine-friendly, and universal. Every modern API uses it. Which means your flows will see it — a lot.

🧠
Mental modelJSON is like a shipping label. It has fields (name, address), and each field has a value. Apps agree on the label format so nobody has to guess.
03 · What Parse JSON is

A translator for your flow.

When an API responds, Power Automate sees one big string of text. It has no idea that "temp" is a number or that "city" is a word. Parse JSON hands the flow a dictionary: "here's what each field means, here's its type, here's its name."

Without Parse JSON

{"city":"Mumbai","temp":32}

One big blob. Can't pick fields.

→
With Parse JSON

city temp

Two clickable chips. Drag anywhere.

💡
Key ideaParse JSON doesn't change your data. It changes how Power Automate sees your data. That's it.

05 · Anatomy

Four moving parts. That's all.

Tap any part below to see what it does.

📥 Content — the raw JSON▼
This is usually body('HTTP_action_name'). It's the raw text that the previous action returned. Paste it (or reference it dynamically).
🧬 Schema — the shape definition▼
A small JSON block that describes every field and its type. You don't write this — Power Automate generates it when you click "Generate from sample".
📤 Outputs — dynamic content chips▼
Once parsed, every field appears in the dynamic content panel. Drag it into any downstream action. Each chip is body('Parse_JSON')?['fieldName'] under the hood.
🔗 Downstream — where the magic happens▼
Send fields to Teams, SharePoint, Excel, Outlook, another API — anything. The parsed fields behave like real variables.
06 · Schema

The schema is just an ID card.

A schema says: "these fields exist, here are their types, some are optional". Once Power Automate has this ID card, it can validate responses and offer you clean chips.

{ "type": "object", "properties": { "id": { "type": "integer" }, "name": { "type": "string" } } }
🧠
Mental modelThink of the schema as a passport check. Without it, Power Automate can't verify the shape of the incoming data. With it, every field becomes legal to use.
⚡
ShortcutYou almost never hand-write a schema. Click Generate from sample and Power Automate builds it for you.
07 · Generate from sample

The 3-click setup.

This is the button that saves beginners hours. Here's exactly what to click.

Step 1

Add the Parse JSON action to your flow, right after the HTTP or connector action.

Step 2

Click Generate from sample and paste a real JSON response.

Step 3

Click Done. The schema appears. Fields show up in dynamic content.

Step 4

Set the Content field to body('YourHTTP') from the previous action.

⚠️
Most common mistakeDon't paste dynamic content into the sample box. Paste a static, full, real example. If you paste a partial response, only those fields become available.
08 · Nested JSON

Objects inside objects.

Real APIs nest data. A user object contains an address object, which contains a city field. Parse JSON handles this — you just need to know how to reference it.

{ "user": { "name": "Alice" }, "address": { "city": "Mumbai" } }

To get the city, chain the reference pattern:

body('Parse_JSON')?['address']?['city']
💡
The patternEvery level down = another ?['key']. Read it left to right like directions: "go into address, then into city".
09 · Arrays

When JSON hands you a list.

Sometimes the response isn't one object — it's an array of objects. A list of orders. A list of employees. A list of support tickets.

[ { "id": 1, "name": "Alice" }, { "id": 2, "name": "Bob" } ]

Parse JSON handles it. But you can't read individual fields directly — you need to loop. Drop in an Apply to Each and reference the parsed array as its input.

🧠
RuleObject response → access fields directly. Array response → wrap in Apply to Each first.
10 · Pitfalls

Five traps beginners fall into.

Tap each to see why it happens and how to avoid it.

1. Pasting dynamic content as the sample▼
The schema builder needs a static JSON example. Dynamic content is empty at design time, so the schema comes out empty. Paste a real, pasted-in sample instead.
2. Using an incomplete sample▼
If your sample has 2 fields but the real API returns 5, only 2 chips are available. Always paste the fullest response you've ever seen from that API.
3. Wrong schema type (object vs array)▼
If the response is [{ ... }], type is array. If it's { ... }, type is object. Mixing them up breaks downstream actions silently.
4. Forgetting empty responses▼
If the API returns nothing (empty string, 204 No Content), Parse JSON fails. Guard with a Condition action checking empty(body('HTTP')) first.
5. Using outputs() instead of body()▼
Parse JSON's output lives in body('Parse_JSON'). Using outputs() returns the whole wrapped envelope, not the parsed fields. That's the #1 expression mistake.

12 · Bug hunt

Spot the mistake.

A flow posts a Teams message with a parsed ticket ID. But it keeps failing. Here's the expression used:

outputs('Parse_Ticket')?['ticketId']

Why does this break?

Pick the correct fix
Add a ? before outputs
Replace outputs() with body()
Wrap the expression in string()
Why: Parse JSON outputs live in body('Action_Name'). Using outputs() returns the whole action envelope — not your parsed field. This is the single most common expression mistake in Power Automate.
13 · Best practices

Write Parse JSON like a senior dev.

  • Rename the action. Parse_Ticket is ten times easier to debug than Parse_JSON_2.
  • Paste a real, complete sample. Made-up examples produce made-up schemas.
  • Guard against empty responses. Wrap with a Condition checking empty().
  • Use ? for optional fields. ?['phone'] returns null instead of crashing when the field is missing.
  • Fall back with coalesce(). coalesce(body('Parse')?['phone'], 'Not provided') keeps your flow safe.
  • Comment your schema. Add a Note action above Parse JSON storing the sample used to build it.
14 · Compare

Parse JSON vs Compose — settle it forever.

Parse JSON

Reads the shape.

Needs a schema. Exposes typed fields. The reader.

Use when: the previous action returned raw JSON.

Compose

Holds a value.

Stores whatever you give it. The writer.

Use when: you want to build JSON or stash an intermediate value.

💡
One-linerCompose writes JSON. Parse JSON reads it.

16 · Quiz

Lock it in.

Three questions. Wrong answers explain themselves.

1. What does Parse JSON actually do?
Converts strings to numbers
Turns raw JSON into typed dynamic content
Sends data to an external API
Right answer: Option 2. It reads the structure and exposes each field as a chip. It doesn't transform the data itself.
2. How do you reference a parsed field?
outputs('Parse_JSON')?['name']
body('Parse_JSON')?['name']
triggerBody()?['name']
Right answer: Option 2. Parse JSON's parsed fields live in body(), not outputs().
3. Best sample for the schema builder?
A made-up minimal example
A real, full response from the API
Any JSON you find online
Right answer: Option 2. Only a real, complete response produces a schema that covers all fields.
