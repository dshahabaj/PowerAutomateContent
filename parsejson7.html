03 — What Parse JSON does

A translator between raw text and typed fields

Parse JSON reads the raw JSON string, matches it against a schema, and exposes every field as dynamic content.

Before Parse JSON

{ "id": 1, "name": "Alice" }

After Parse JSON

Every field becomes a chip you can drag into any action:

id name email

🎬 On screen: Show the Parse JSON action in the designer. Highlight where the "Content" comes from (the HTTP body). Show that after parsing, dynamic content chips appear below the action.
🎙️ Narration script

Parse JSON is basically a translator.

It takes the raw string from your HTTP action and reads it against a schema — a definition of what the JSON should look like. Once it understands the shape, it exposes every field as a dynamic content chip.

So this — a blob of text — becomes this. A set of usable fields: id, name, email.

Important thing: Parse JSON doesn't change the data. The data is still the same. It just tells Power Automate the shape so it can use it.

06 — Anatomy

The anatomy of Parse JSON

Four parts you need to know:

📥 Content

The raw JSON string — usually from the previous action's body.

🧬 Schema

The shape definition. Power Automate generates it from a sample.

📤 Outputs

Typed dynamic content chips — one per field in the schema.

🔗 Downstream

Use the fields in any action below via body('Parse_JSON')?['key'].

🎬 On screen: Show the Parse JSON action in the designer. Point to the "Content" field. Point to the "Schema" field. Then show the OUTPUT section in run history where fields appear. Then show a downstream action using one of these fields.
🎙️ Narration script

Let's break down Parse JSON into four parts.

First — Content. This is the raw JSON string. Usually it's the body of the previous HTTP action.

Second — Schema. This is the shape definition. It tells Power Automate what fields to expect and their types. You almost never write this by hand — Power Automate generates it from a sample.

Third — Outputs. Once parsed, every field becomes a typed dynamic content chip. One per field. These are what you drag into downstream actions.

Fourth — Downstream. You access the fields anywhere below using the expression body, followed by the action name, followed by the field key.

Content is what you parse. Schema is how. Outputs are what you get. Downstream is where you use it.

A schema describes the structure: which fields exist, their types, and which are required.

🎙️ Narration script

Let's walk through a real example.

Here's the JSON. id, name, email, active. Simple, flat object.

After parsing, you access any of these fields using this expression — body of Parse JSON, followed by the field key in brackets.

So for email, it's body('Parse_JSON')?['email']. Notice the question mark before the bracket — that's called a null-safe accessor. If the field doesn't exist, Power Automate returns null instead of crashing.

10 — Example 2

Nested object — objects inside objects

{ "id": 101, "user": { "name": "Shahabaj", "email": "s@example.com" }, "address": { "city": "Mumbai", "country": "India" } }

Access nested fields by chaining:

body('Parse_JSON')?['user']?['name'] body('Parse_JSON')?['address']?['city']
🎬 On screen: Show a nested JSON parsed in Power Automate. Expand the run history output. Show how nested fields appear with their own sub-levels. Then show a Compose action accessing the city field.
🎙️ Narration script

Now let's look at nested objects.

Real APIs often nest data. Look at this — the user object is inside the main response. And address is also inside.

After parsing, you access these by chaining the pattern. So to get the user's name, it's body of Parse JSON, then user, then name. Same pattern for city — body, then address, then city.

Each nested level uses that question mark and bracket. It's like walking down a folder structure. You just add one step for each level of nesting.

One important tip — if you're not sure whether a field exists, the question mark saves you. It returns null instead of throwing an error.

11 — Example 3

Array of objects — when JSON returns a list

[ { "id": 1, "name": "Alice" }, { "id": 2, "name": "Bob" }, { "id": 3, "name": "Cara" } ]

Schema type is array. Loop through with Apply to Each and access item()?['name'].

🎬 On screen: Show an array-parsed output. Show the Apply to Each loop. Inside the loop, show the expression item()?['name'] in a Compose action. Run the flow and show each item being processed.
🎙️ Narration script

Now let's talk about arrays.

Sometimes the API returns a list of items instead of a single object. Look at this — three users, each with an id and name.

When the top-level type is an array, Power Automate knows it's a list. You handle this with an Apply to Each loop.

Inside the loop, you access the current item using item()?['name']. Not body. Not triggerBody. item.

That's the pattern for arrays. body for parsed objects at the top level. item inside a loop.

If you mix those up, you get null values or errors. So remember: top-level uses body, loop uses item.

12 — Example 4

Mixed types — including null

{ "name": "Order #101", "amount": 249.99, "paid": true, "discount": null, "tags": ["urgent", "vip"] }
Watch out for null

Use coalesce(body('Parse_JSON')?['discount'], 0) to provide a fallback.

🎬 On screen: Show a parsed JSON with mixed types in the run history. Highlight how the null field appears. Then show a Compose action using coalesce to provide a default value.
🎙️ Narration script

Real APIs mix types. Here's what that looks like.

You have name — a string. amount — a number with decimals. paid — a boolean. discount — null. tags — an array of strings.

Parse JSON handles all of these. No problem.

But here's the trap — null fields. If your API sometimes returns null for a field, and you use that field downstream, your flow might fail. Because null doesn't behave like a real value.

Fix that with coalesce. Coalesce takes two values and returns the first one that isn't null. So coalesce of discount and 0 returns either the discount, or 0 if discount is null.

Always handle null explicitly. It's the difference between a flow that works and one that breaks at 2 AM.

15 — Access patterns

Every way to reference parsed fields

// Top-level field body('Parse_JSON')?['name'] // Nested field body('Parse_JSON')?['user']?['email'] // Array element (inside Apply to Each) item()?['amount'] // Array index (when you know the position) body('Parse_JSON')?['tags']?[0] // With fallback for null coalesce(body('Parse_JSON')?['discount'], 0)
🎬 On screen: Show these five patterns on screen in a Compose action or the expression editor. Type each one so the viewer sees the exact syntax.
🎙️ Narration script

Let me leave you with the five patterns you'll use again and again.

One — top-level field. body of Parse JSON, then the field name.

Two — nested field. Chain the pattern. body, then user, then email.

Three — array element inside a loop. item, then the field name.

Four — array index when you know the position. body, then tags, then index zero. That gets you the first item.

Five — with a fallback for null. Coalesce wraps the whole thing and provides a default.

Memorize these five. They cover 95% of real-world cases.

21 — Compare

Parse JSON vs Compose

Parse JSON

Reads the shape. Interprets JSON structure. Needs a schema. Great for API responses.

Compose

Holds a value. Static. Doesn't interpret structure. Perfect for building JSON.

🎬 On screen: Show both actions side by side in the designer. Show a Compose action that builds JSON. Show Parse JSON that reads JSON.
🎙️ Narration script

One quick comparison before we move on — Parse JSON vs Compose.

Parse JSON reads the shape. It interprets JSON structure. It needs a schema. And it's perfect for API responses.

Compose holds a value. It's static. It doesn't interpret anything. And it's perfect for building JSON or holding computed values.

Think of it this way — Compose writes JSON. Parse JSON reads it. Different tools for different jobs.

27 — Pitfalls

Six common mistakes

1. Dynamic content as the sample

Paste a static JSON sample, not dynamic content. Otherwise the schema generation fails.

2. Incomplete sample

If your sample has 2 fields but the real response has 5, only 2 will be available downstream.

3. Wrong schema type

Object vs Array matters. { } is object. [ ] is array.

4. Empty responses

Guard with empty() before parsing. Otherwise Parse JSON fails.

5. outputs() instead of body()

Parse JSON outputs live in body('Parse_JSON'), not outputs().

6. Not handling null

Wrap with coalesce() for a fallback value.

🎬 On screen: For each mistake, show what it looks like in the designer when the mistake is made. Show the correct fix.
🎙️ Narration script

Let's talk about the six most common mistakes.

One — using dynamic content as the sample. When you click Generate from sample, paste static JSON. If you paste dynamic content, it won't work.

Two — using an incomplete sample. If your sample only has 2 fields but the real response has 5, only 2 will be available downstream. Always use a real, complete response.

Three — wrong schema type. Object versus array. If the response is curly braces it's an object. If it's square brackets it's an array. Getting this wrong breaks everything downstream.

Four — not handling empty responses. If the API returns nothing, Parse JSON fails. Guard with a Condition first.

Five — using outputs instead of body. Parse JSON outputs live in body of Parse JSON. Not outputs.

Six — not handling null. Wrap null-sensitive fields with coalesce.

Avoid these six and your flows will be rock solid.

28 — Best practices

Write clean Parse JSON actions

  • Rename every action — Parse_Weather, not Parse_JSON
  • Generate the schema from a real, complete response
  • Store the sample in a comment or documentation
  • Test with empty or malformed responses
  • Use ?['key'] for optional fields
  • Validate the response before parsing
🎬 On screen: Show a well-named Parse JSON action. Show the flow structure. Show where the sample is documented.
🎙️ Narration script

Here are the best practices I follow.

Rename every action. Not "Parse_JSON" — instead "Parse_Weather" or "Parse_User_Response". Your future self will thank you.

Generate the schema from a real, complete response — not a mockup, not a guess.

Store the sample somewhere. A comment, a doc, a wiki. Because when the API changes, you'll need it.

Test with empty or malformed responses. It's not if the API fails — it's when.

Use question mark brackets for optional fields. And validate the response before parsing when you can.

Six practices. Follow them and your flows will hold up in production.
